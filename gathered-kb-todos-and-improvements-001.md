## 1. Where we left off

The project re-implements five Informatica IDQ stage-load workflows of the Member domain: ECI, FSS, TTF, WIC and
TRS Ongoing, 38 mappings in all, exported as `docs/wf_*.xml`. The same workflows are now described or replaced in
**four** ways:

| Deliverable | Folder | Coverage | State |
|---|---|---|---|
| **Java / Spring Boot rewrite** (CLI + REST) | `src/` | 33 mappings. The 5 deactivation / reactivation mappings are out of scope. | Builds; ~40 unit tests (one PKEY test per mapping) pass. `OracleWorkflowIT` **passed for ECI only**. `SourceEntitiesIT` **never run**. |
| **Business documentation** for the Java port | `docs/mappings/` (`000`–`033`) | 33 mappings + mapplets | Hand-maintained. Lookup sections are generated by `ext-tools/lookups.py` + `render_lookups.py`. |
| **IDMC CDI / CDQ build specs** | `idmc/<workflow>/` | all 38 mappings, all mapplets, taskflows, parameter files | Fully generated by `ext-tools/idmc_spec.py`. Includes *Filtered data* and *Oracle stored procedure* sections. The timeline is left out. |
| **PowerCenter conversion** | `idq-to-pc/wf_ECI_Stage_Load/` | ECI only | Importable XML from `ext-tools/idq_to_pc.py`, with a manual-work list in `conversion_report.md`. Never imported into a real PowerCenter. |
| **Oracle stored procedures** | `idq-to-oracle/` | all 38 mappings | `sp_ors_main_<mapping>`, shared helpers, `fn_dq_*` contract, install and run scripts. The timeline **is** ported and marked `/* TIMELINE */`. **Never compiled.** |

## 4. Process improvements

1. **One source of truth per kind of knowledge.** Today the same mapping is explained in `docs/mappings`
   (hand-written), `idmc/` (generated), the Oracle procedure headers (hand-written) and `common_insights.md`. Prefer
   generating from the XML (as `idmc/` does) and keep hand-written text for *business* meaning only. Record each
   new quirk once in `common_insights.md` and link to it.
2. **A three-way regression harness.** The same input runs through IDQ (or its recorded output), Java and Oracle,
   then a diff per `C_S_*` table by `PKEY_SRC_OBJECT`. This turns "matches IDQ" from a claim into a check. The
   `adhoc_runs_*` reports and `etl_process=IDQ|JAVA` are most of the plumbing already.
3. **Run the Oracle integration tests in CI**, or at least on every PR that touches `source/` or `mdmdc/`. The two
   ITs fell behind for several PRs because they need the wallet.
4. **Configuration snapshot.** Export `EXC_LOOKUP_CODE_VALUE`, `LOOKUP_CODE_VALUE` and `V_LOOKUP_CODE_VALUE` with
   each test run. Results depend on them (exception codes, translations).
5. **Decision log.** Record D1–D10 answers (with date and who decided) next to this file, and apply them in all ports
   at once, so Java, Oracle and the specs never drift apart silently (D3 already has).
6. **Regenerate, don't edit.** `idmc/` is generated (`for f in docs/wf_*.xml; do python -I ext-tools/idmc_spec.py
   "$f" "idmc/$(basename "$f" .xml)"; done`), and so are the lookup sections of `docs/mappings`. Hand edits there
   are lost on the next run.
7. **Keep PRs small and themed**, as in #13–#17. Each PR had one purpose and an honest test plan, which made this
   recap possible.
8. **Before re-exporting from IDQ**, clean the export (D9) so stale filters and SQL fragments do not become live.

  enough to find it).
- `SampleData` dispatches by method name (`fill_sample_mock_data_<mapping>`). A map of mapping → supplier would be

- Bring in the 5 missing mappings (P2), with the Oracle procedures as the reference.
- Plug a real `AddressValidator` bean.

**Oracle (`idq-to-oracle/`)**

- Compile and test (P1).
- Add `LOG ERRORS` on the `EXC_STG_BAD_REC_MEMB` inserts, to survive the unique key on `RUN_DATE` the way IDQ does
  ([insights §12](docs/common_insights.md#12-risks-when-re-platforming)).

- Mark the lookup helpers `RESULT_CACHE` / `DETERMINISTIC` if volumes need it.
- `fn_ors_helper06_common` (blank test) is defined but unused. Use it or drop it.

**ext-tools**

- Evaluate simple conditions (e.g. a `DECODE` that only returns `'40'` / `'100'`) so *Filtered data* can say "default
  group never reached".
- Generate the Oracle procedure skeletons (target column lists, unfed ports, truncate flags) from the same model as
  `idmc_spec.py`, so that only the expressions are hand-written.

## 7. Ground rules learned along the way

- **Never run `docs/*_EXPORT_OCT_16.sql`.** They start with `DROP TABLE`.
- **Never drop tables from the app.** A full delete only happens for tables listed in `clearable-tables.txt`.
- **Ignore `*BAK*` / `*BKP*` / date-stamped tables.** Do not model, mock, test or report them.
- **Entity naming:** `_D_` tables get the `Delta` suffix and `_H_` tables the `Hist` suffix (`STG_ECI_D_CHILD` →
  `ChildDelta`).
- **Timeline columns are stale.** Leave them out, except in the Oracle port, where they were kept on request and
  marked.
- **Insert with `insertAll`, never `save`.** Keys are assigned, so `save` would issue an `UPDATE`.
- **Build with JDK `C:\Users\vamsi\jdk\zulu27` and Maven 3.9.9.** Pass properties as `-D...` before `-jar`.
- **Python tools run with `python -I`**, from the repo root.
- **WIC is a fifth source**, beyond the four in the original instructions.

## 8. Suggested restart checklist

1. `git switch main && git pull`, then read this file and `docs/common_insights.md` §1.
2. `mvn test` to confirm the unit tests still pass on the current JDK.
3. Decide whether the new functionality depends on any P1 item. If it touches the database, run
   `OracleWorkflowIT` for ECI first as a smoke test.
4. Pick up open business decisions D1–D10, if answers have arrived.
5. Start the new work on its own branch. Add new findings to `docs/common_insights.md`, and new open items to a
   `gathered-kb-todos-and-improvements-002.md`.
