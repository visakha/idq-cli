Each mapping spec in `idmc/<workflow>/mappings/<mapping>.md` has an **Oracle stored procedure** section with what
the procedure does, its parameters, the tables it writes and the shared objects it calls. Each workflow README in
`idmc/` lists the procedures in taskflow order. Both sections are generated by `ext-tools/idmc_spec.py` from the
`.sql` headers here, so after changing a procedure header, regenerate:

```sh
for f in docs/wf_*.xml; do python -I ext-tools/idmc_spec.py "$f" "idmc/$(basename "$f" .xml)"; done
```

> **Not compiled.** No Oracle database was available while these were written. Compile them in a scratch schema
> (with the contract stubs) before use, and compare the results with an IDQ run on the same input.

> **Insert only.** The procedures never `TRUNCATE`, `DELETE` or `DROP`, so they are safe to call against production
> data. The IDQ *Truncate target table* option and the `DD_DELETE` update strategies are deliberately not carried
> over: every such place is marked `-- Not performed: ...`. A second run on the same data therefore adds the rows
> again (or fails on a unique key) unless the targets are emptied beforehand, outside this code base.

## Naming

| Object | Name | Where |
|---|---|---|
| One procedure per IDQ mapping | `sp_ors_main_<mapping name>` | `<workflow>/sp_ors_main_<mapping>.sql` |
| Data-quality function per IDQ mapplet / rule (assumed to exist) | `fn_dq_<what>` | contract in `common/02_dq_functions_contract.sql` |
| Their return types | `t_dq_<what>` | `common/01_dq_types.sql` |
| Helpers shared by several mappings | `fn_ors_helperNN_common`, `sp_ors_helperNN_common` | `common/03_ors_common_helpers.sql` |
| Helpers used by one mapping only | `fn_ors_helperNN_<mapping>`, `sp_ors_helperNN_<mapping>` | none were needed: every mapping is a single set-based statement (or a few) |

## Install

Requires **Oracle 12.2 or later**: several procedure names are longer than 30 characters (the longest,
`sp_ors_main_m_Tgt_C_S_TRS_Pty_Mng_Attr_Auth_Rep_Ongoing`, is 54). The SQL also uses `OUTER APPLY`, `CROSS APPLY`
and `FETCH FIRST`, which need 12c.

Install as the schema that owns, or has synonyms for, the staging tables. Tables are referenced unqualified, as in
the IDQ mappings (including `C_B_*` hub tables, `V_LOOKUP_CODE_VALUE` and `EXC_LOOKUP_CODE_VALUE`).

```sql
-- from this folder, in SQL*Plus or SQLcl
@install.sql
```

[install.sql](install.sql) runs, in order:

1. `common/01_dq_types.sql`: the object types that the `fn_dq_*` functions return.
2. `common/02_dq_functions_contract.sql` is **commented out**. It holds stubs with the agreed names and signatures,
   whose bodies raise ORA-20999. Run it only in a scratch schema to compile the procedures. Never run it where the
   real functions exist, because it would replace them.
3. `common/03_ors_common_helpers.sql`: the shared helpers.
4. Every `sp_ors_main_*`, workflow by workflow.

It ends by listing any invalid object.

## Run

Run a whole workflow with `@<workflow>/run_<workflow>.sql`, or call a single procedure such as
`EXEC sp_ors_main_m_Tgt_C_S_ECI_Pty`. The run scripts follow the taskflow order in `idmc/<workflow>/taskflow.md`.
Where IDQ runs mappings in parallel, the scripts run those paths one after another and keep every dependency. The
IDQ command task (`touch <workflow>.ind`) is left to the scheduler.

From the CLI, start with `-Detl_process=ORA_SP -Dmock_ora_sp=false` and use `run-etl`. `OraSpRunner` reads the `EXEC`
lines of the run script (folder set by `idq.ora-sp.dir`, default `idq-to-oracle`) and calls each procedure over JDBC
in that order. It stops at the first failure, and the run is audited in the `adhoc_runs_<SOURCE>/*_$ORA_SP$_*.md`
reports. Keep each run script to one `EXEC sp_ors_main_<mapping>` per line without arguments, because the CLI reads
only lines in that form.

## How a mapping becomes a procedure

| IDQ | Oracle |
|---|---|
| Mapping | `sp_ors_main_<mapping>`. One transaction: `COMMIT` at the end; on any error `ROLLBACK` and re-raise |
| User parameter `$Name` | procedure parameter `p_name` with the IDQ default |
| `$sys.MappingRunStartTime`, `SYSTIMESTAMP()`, `RUN_DATE` | `l_run_ts`, taken once at the start of the procedure |
| `$sys.MappingName` | constant `c_mapping` |
| Target option *Truncate target table* | **Not performed.** The procedures never truncate, delete or drop; they only insert. A comment `-- Not performed: IDQ "truncate target table" of ...` marks the place. Empty the targets yourself (outside this code base) before a run if you want IDQ's result |
| Source with custom SQL | the SQL copied verbatim into a CTE. A source filter or *select distinct* stored next to custom SQL is ignored, because IDQ ignores it too |
| Expression, Filter, Joiner | SQL expressions, `WHERE`, joins |
| Lookup on reference data | helper function (`fn_ors_helper03/04/05/08_common`) |
| Lookup on a table the run also writes | `OUTER APPLY … FETCH FIRST 1 ROW ONLY` or `NOT EXISTS` inside the same statement, which sees one consistent snapshot, like IDQ's static lookup cache |
| Mapplet / rule | `fn_dq_*` call in a `NO_MERGE` CTE, read as `alias.obj.attribute` |
| Router with several groups and targets | one `INSERT ALL` with a `WHEN` per group. As in IDQ, a row goes to every group it matches |
| Sorter (distinct) | `DISTINCT` |
| Aggregator without aggregate functions | `ROW_NUMBER()` picking the last row of the group in IDQ sort order (IDQ sorts NULL high) |
| Normalizer | `UNPIVOT` or a pipelined `fn_dq_norm_*` with `CROSS APPLY TABLE(...)` |
| Update strategy `DD_DELETE` | **Not performed** (marked `-- Not performed: the IDQ DD_DELETE of ...`): `STG_<SRC>_PTY_INACTIVE_STS` keeps the status rows of reactivated parties and `STG_TRS_VALID_MEMBERS` keeps deactivated members |
| IDQ blank test `LENGTH(RTRIM(x)) = 0 OR ISNULL(x)` | `RTRIM(x) IS NULL` (in Oracle, `''` is NULL) |
| Target port with no link | written as explicit `NULL`, listed in the header |

## Timeline (ported here, and marked)

The IDMC/CDI specs and the Java port leave out the legacy MDM timeline of the `C_S_*` tables. For this Oracle port it
**is** implemented, so the procedures write exactly what IDQ writes. Every such expression is marked with a
`/* TIMELINE */` comment, and each procedure header has a *TIMELINE* paragraph that describes it:

- `VERSION_SEQ` is a running number or rank per key, `SRC_ROWID = key || '|' || VERSION_SEQ`, and the version and
  duplicate ranks and their filters are kept;
- `PERIOD_REFERENCE_TIME`, `TIMELINE_ACTION` and `PERIOD_START_DATE` / `PERIOD_END_DATE`;
- `mplt_DST_Correction` becomes `fn_dq_dst_correction`;
- `mplt_Pty_Rle_Rel_Timeline_Validation` is inlined. It corrects the end date for DST, emits each end-dated
  relationship twice (closed, plus an open copy), re-ranks `VERSION_SEQ` and sets `HUB_STATE_IND`.

To drop the timeline later, remove the marked expressions (and write NULL or the plain key).

## IDQ behaviour carried over on purpose

These are reproduced as IDQ runs them and explained in the procedure headers:

- **`m_Tgt_Stg_ECI_Pty_Reactivation_D_Medicaid`**: the IDQ filter tests the source key instead of the lookup result,
  so IDQ writes no rows. The default `p_test_lookup_result => 'N'` reproduces that. Pass `'Y'` for the intended
  behaviour.
- **`m_Tgt_C_S_FSS_Pty_Validation`**: writes the *Reactivation* row into the STS table, not the LOG table. (IDQ then
  deletes the older STS rows of those keys; that delete is not performed here.)
- Exception rows write the **looked-up** exception code where the mapping does (NULL when the code is not in
  `EXC_LOOKUP_CODE_VALUE`), and the computed code elsewhere.
- Unlinked router or sorter ports (for example `FLR_NUM`, `LCTN_CRDNT_DESC`) are written as NULL.

## Open risks

- **`UQ_EXC_STG_BAD_REC_MEMB`**: the table is unique on (`SRC_SYS`, `SRC_SYS_ID_1..3`, `EXCEPTION_TYPE`,
  `EXCEPTION_CODE`, `RUN_DATE`), and `RUN_DATE` is the run start for every row. A source with duplicate keys can
  produce two equal exception rows in one run.
  - IDQ rejects only the duplicate row and carries on.
  - Here the whole statement fails and rolls back.
  - If that happens, add `LOG ERRORS INTO err$_exc_stg_bad_rec_memb REJECT LIMIT UNLIMITED` to the `INTO
    EXC_STG_BAD_REC_MEMB` clause (after `DBMS_ERRLOG.CREATE_ERROR_LOG`), which matches IDQ row-error behaviour.
- **Commit granularity**: IDQ commits per target as it writes. The procedures commit once at the end, which is
  safer, but undo use grows with volume.
- **`fn_dq_*` semantics**: the procedures assume the contract in `02_dq_functions_contract.sql`, which is one row in
  and one object out with the mapplet's outputs. Compare the real implementations with the IDQ mapplets on a sample.
- **Performance**: functions are called per row from SQL. Make them `DETERMINISTIC`, or use `RESULT_CACHE` for the
  lookup helpers, if volumes need it.
